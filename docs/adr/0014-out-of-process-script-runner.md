# Scripts and the shell run in a child process, killed on timeout or end of session

User scripts ran in the main process inside `node:vm`. That has two problems, and only one was a bug anyone had hit. A script of `while (true) await Promise.resolve()` never lets the event loop turn, so the wall-clock timer that was meant to stop it could never fire, and the whole app froze until the user force-quit; `vm`'s own `timeout` only covers the synchronous part of a run. And `node:vm` is not a sandbox: a script can reach Node primordials through host-realm objects, so it sat in the process that holds the secrets vault, the SQLite database and every connection's live client.

**Decision.** `ScriptService` becomes an orchestrator and the script runs in an Electron `utilityProcess` (`electron/script-runner/runner.ts`, built to `dist-electron/script-runner.cjs`). One process per run. Main posts a single request over the message port and waits for one message back.

- **Timeout and cancel are kills.** One wall-clock timer per run covers spawn, connect, run and result encoding; when it fires, or cancel arrives, or the app quits, main kills the process and rejects with the same `TIMEOUT` errors as before. This is the only mechanism that bounds all three runaway shapes (sync loop, microtask loop, a promise that never settles), because the runner shares no event loop with main.
- **The runner holds no `MongoClient`, URI or credentials.** Its `db` is a facade (`rpcClient.ts`) whose every call becomes an RPC frame to main; main executes it in `rpcHost.ts` through `makeDbProxy` over the pool's own client, after a per-object method allowlist, with the connection's read-only flag read live on every call. Cursors are main-side handles, closed when the run ends, is killed, or the child dies. Arguments and results cross as canonical EJSON strings. The child gets an allowlisted environment rather than a copy of main's, and nothing connection-related in its request. The first version of this decision gave the runner its own client and the credentials to build it; the bridge replaced that, so there is no `connectionSpec` any more.
- **Main still connects first** (`pool.readClient`), so connect errors and status events are unchanged, and that client is the one the run uses: there is no second connection per run.
- **A child that dies before answering** is a `SystemError`, never a hang. Children are killed on quit.
- **The Mongo shell uses the same runner.** `ShellService` spawns one long-lived child per session through the same `RunnerSpawner` and the same bundled entry; its first message is a `shell-start` request instead of a `run`, and it runs `repl.start` over in-memory streams (`shellSession.ts`). Its `db` is the same RPC facade, answered by an `rpcHost` that `ShellService` creates per session over the pool's client, with the read-only flag read live. Main posts input lines after `rewriteShellSugar` and forwards the child's output unchanged to the `mshell:output-event` emitter, so the IPC channels and the renderer contract did not change. The session ends when it is stopped, when its connection disconnects or turns read-only, when the REPL exits, or at quit; ending it kills the child and closes the host. A child that dies on its own ends the session with an error event. Read-only on the shell is still a wholesale refusal at `start` and `write` (ADR 0005): the REPL is not a sandbox and cannot tell a read from a write.

## What this does and does not protect

**Read-only on the script pane is enforced in main, for every route.** A write on a read-only connection is refused where the call arrives, by the same `dbProxy` allowlist and the live flag, whichever way the script reached it: a collection call, `getCollection`/`collection`, a cached method reference, `admin()`, `runCommand`, an aggregate with `$out`/`$merge`, or a frame posted by hand from a script that has escaped its `vm` context. The facade is a convenience; the host's allowlists are what hold. A flag flip is honoured by the next call, not only by stopping the run.

**An escaped script, or a `require('child_process')` typed into the shell, holds no credentials.** The child has no URI, password, TLS material or client, and nothing main sends it carries any. To use the connection it must send frames, which main checks. It also has no route to main's memory, the secrets vault, SQLite, or other connections, and can no longer freeze the app.

**What it still has.** The child is an ordinary process of the same OS user, so an escaped script keeps that user's files, processes and network. Against a deployment that needs no authentication (a local `mongod` with auth off) it can open its own connection straight to the server and write regardless of the app's read-only setting, because there are no credentials to withhold. That cannot be closed from inside the app. **MongoDB roles remain the authoritative control**: for a hard guarantee, connect with a database user that only holds read privileges. This ADR does not claim more than that.

Results of database calls are now encoded in main, synchronously, on main's event loop. That takes about 50 ms for a 10 MB result and grows toward the 50 MB cap, and the wall-clock kill does not bound it: the kill only acts between event-loop turns. It is the same trade as the UI query path, which encodes in main as well. A run is also held to 64 calls in flight and 16 MiB of arguments per call, so an escaped script flooding the bridge gets errors for the excess rather than unbounded work on the shared client; that limits the queue, it is not a rate limit.

A connection flipped to read-only mid-run is refused on the next write by the live check, and additionally stops its scripts: `ConnectionService.update` announces the flip on the pool and `ScriptService` kills that connection's runners with a read-only refusal, so a script started on a writable connection does not carry on. A connection that goes away mid-run (Disconnect, Cancel-connect, delete, a host edit that reconnects) stops its scripts too, through the pool's `disconnected` status, because the client the host executes on is closed with it.

## Considered Options

- **`vm` with `microtaskMode: 'afterEvaluate'`.** Makes the `vm` timeout cover microtasks queued in the context, but breaks any script that awaits a host promise, which is every `db` call. Rejected.
- **A pool of warm runners.** Measured before deciding: a fork plus `require('mongodb')` plus connect plus a trivial script is about 70 ms bundled (110 ms as `.ts`) under Node against a local `mongodb-memory-server`, and 120-140 ms end to end through the packaged app. That is not worth a pool's lifecycle, cross-run state and cleanup. Revisit if runs against a remote TLS or Atlas cluster make the per-run handshake the bottleneck.
- **A per-run or per-session child with its own client** (the first version of this decision). Replaced by the bridge, see above; the shell never shipped that way.
- **A sandboxed renderer window as the runtime.** A separate, larger piece of work; not scheduled.

## Consequences

- The bridge's callable surface is a fixed list (`rpcSurface.ts`), and the facade carries less than the driver did. Not carried: `watch`, the bulk builders, `db.aggregate`, `db.collections`, and the aggregation-cursor builders (`out`, `merge`, `group`, `match`, ...), since each hands back a live driver object or appends a write stage after the read-only pipeline check. A call to one is a `TypeError`. Results must be plain data; a driver object is refused rather than serialized, because it reaches the client and through it the connection options.
- Every database call is a message round trip, and a large result is built and encoded in main. Measured against a local `mongodb-memory-server` under Node: an empty run is about 60 ms (it was about 115 ms with a client of its own, which connected per run), a loop of 1000 `findOne` is within noise of before (about 0.12 ms net per call either way), and a 10 MB `toArray` takes about 140 ms against about 150 ms. The encode of that 10 MB result runs on main's event loop: a loop-gap probe saw one stall of about 50 ms. A script that returns a result near the 50 MB cap will stall main for proportionally longer, and the runner's kill does not bound it.
- The runner entry is a second CommonJS build target (`vite.config.ts`, a second `preload` item), loaded by `utilityProcess` from inside `app.asar`. It now requires only `bson`, `node:vm` and, for the shell, `node:repl`; `mongodb` is no longer in its graph. The packaged-build check below predates the bridge and was made on the earlier runner, which bundled the driver: macOS arm64, unsigned, `electron-builder --dir`, with the release fuses applied (`OnlyLoadAppFromAsar`, `RunAsNode` off) and driven over the Chromium debugging port, where `asarUnpack` was not needed. It has not been repeated for the bridge, and Windows (NSIS), Linux (AppImage) and a signed macOS build were never verified. What is verified for the bridge is the unpackaged app under Electron's `utilityProcess`, by an end-to-end test (`tests/e2e/script-run-cancel.e2e.ts`), as well as under Node by the integration suite.
- The runner must work both bundled as `.cjs` and as plain `.ts` under Node's type stripping, because the integration tests fork the `.ts` file. That rules out top-level `await`, `import.meta` and runtime path aliases anywhere in its import graph.
- A shell session costs one child for its lifetime. Measured against a local `mongodb-memory-server`: start to first output about 80 ms under Node and about 60 ms in the unpackaged Electron app (it was about 1 ms with the REPL in main), and one `await db.x.findOne()` line about 2 ms either way (1.8 ms before, 2.0 to 2.3 ms after, medians). The packaged-build check above has not been repeated for the shell.
- `vm`'s `timeout` is gone; the kill is the single ceiling. Main threads each run's own abort signal into every call and closes the run's cursors when the run settles, so a kill stops the work main started on the script's behalf, not only the child. Cancel itself does not fire the script's `signal` global.
