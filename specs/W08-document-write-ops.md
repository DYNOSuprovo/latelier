# W08 — Document write ops (insert, edit, delete)

## Purpose

Allow users to insert, modify, and remove documents from the active collection. All writes go through main so validation, EJSON round-tripping, and safety guards run server-side. Each operation has a clear UI flow and requires explicit confirmation when dangerous.

## Scope

- **In**: `doc:insert`, `doc:insertMany` (T2.7), `doc:replace`, `doc:updateOne`, `doc:deleteOne`, `doc:deleteMany`, the Insert drawer, the Edit drawer, the Delete confirm dialog, result refresh after writes.
- **Out**: Bulk import/export from file/CSV (deferred), an `ordered: false` / unordered-insert toggle, aggregation-driven updates (A06's `$out`/`$merge` covers that).

## Dependencies

- W03 (EJSON), W05 (selection context), W06 (selection UX), F05 (pool).

## 1. IPC channels

| Channel            | Input                                      | Output                 |
| ------------------ | ------------------------------------------ | ---------------------- |
| `doc:insert`       | `{ connectionId, dbName, collection, docJson: string }` | `{ insertedId: unknown }` |
| `doc:insertMany`   | `{ connectionId, dbName, collection, docsJson: string }` (canonical EJSON array) | `{ insertedCount: number, insertedIds: unknown[] }` |
| `doc:replace`      | `{ connectionId, dbName, collection, filterJson: string, docJson: string }` | `{ matchedCount, modifiedCount }` |
| `doc:updateOne`    | `{ connectionId, dbName, collection, filterJson: string, updateJson: string }` | `{ matchedCount, modifiedCount }` |
| `doc:deleteOne`    | `{ connectionId, dbName, collection, filterJson: string }` | `{ deletedCount }` |
| `doc:deleteMany`   | `{ connectionId, dbName, collection, filterJson: string, confirmToken: string }` | `{ deletedCount }` |
| `doc:confirmUpdateMany` | `{ connectionId, dbName, collection, filterJson: string, updateJson: string }` | `{ count: number, confirmToken: string }` |
| `doc:updateMany`   | `{ connectionId, dbName, collection, filterJson: string, updateJson: string, confirmToken: string }` | `{ matchedCount, modifiedCount }` |

All `*Json` are EJSON canonical strings. `confirmToken` is a nonce generated by main when the user first requests a dangerous-scale delete or update (see §4); this prevents accidental bulk-deletes/bulk-updates via IPC misuse. `updateMany`'s `updateJson` must be an update-operator document (`$set`/`$unset`/`$inc`, …) — a replacement-style document or an aggregation-pipeline array is refused with `VALIDATION`, and its `confirmToken` is additionally bound to a hash of the exact `updateJson` reviewed, so editing the update body after `doc:confirmUpdateMany` invalidates the token even though the filter/collection are unchanged.

## 2. Service (main)

```ts
// electron/mongo/DocumentService.ts
class DocumentService {
  constructor(private pool: MongoPool) {}

  async insert(i: InsertInput) {
    const doc = ejsonParse(i.docJson);
    if (!isPlainObject(doc)) throw validation('docJson', 'must be an object');
    const coll = (await this.pool.getDb(i.connectionId, i.dbName)).collection(i.collection);
    const r = await coll.insertOne(doc);
    return { insertedId: ejsonEncode(r.insertedId) };
  }

  async insertMany(i: InsertManyInput) {
    // T2.7 — a top-level EJSON array routed here by InsertDrawer (see §5).
    const docs = ejsonParse(i.docsJson);
    if (!Array.isArray(docs) || docs.length === 0) throw validation('docsJson', 'must be a non-empty array');
    if (!docs.every(isPlainObject)) throw validation('docsJson', 'must be an array of documents');
    const coll = (await this.pool.getDb(i.connectionId, i.dbName)).collection(i.collection);
    // ordered: true (explicit, deliberate) — stop at the first write error so
    // insertedCount is an honest "how many landed before the failure" count.
    const r = await coll.insertMany(docs, { ordered: true });
    return { insertedCount: r.insertedCount, insertedIds: Object.values(r.insertedIds).map(ejsonEncode) };
  }

  async replace(…) { /* findOneAndReplace — see §3 */ }
  async updateOne(…) { /* finds first matching doc by filter */ }
  async deleteOne(…) { /* deleteOne */ }
  async deleteMany(i: DeleteManyInput) {
    // verify confirmToken; count first; refuse if > 1000 and not confirmed
  }
}
```

Errors:
- `DuplicateKey` (E11000) → `CONFLICT` with readable message naming the duplicate index.
- `DocumentValidationFailure` → `VALIDATION` with `details.schemaErrors`.
- `Unauthorized` → `UNAUTHORIZED`.
- Other Mongo errors → `MONGO_ERROR`.
- `insertMany` only: because `ordered: true` stops the batch at the first write
  error, every error branch above additionally folds `err.result.insertedCount`
  (the driver's `MongoBulkWriteError.result.insertedCount`, when present) into
  `details.insertedCount` — the count of documents that landed before the
  batch stopped. This lets the renderer distinguish a *partial* failure (some
  docs inserted, refresh the grid, keep the drawer open) from a *total*
  failure (nothing inserted, same behavior as single-doc `insert`).

## 3. Replace vs updateOne semantics

- **Replace**: `collection.findOneAndReplace(filter, doc)` — keeps the doc's `_id` if `_id` is in the filter and not in `doc`; otherwise driver rules apply. Used when the user edits the whole JSON payload.
- **UpdateOne**: `collection.updateOne(filter, update)` — `update` must start with `$set`, `$inc`, etc. The Edit drawer's **Update fields ($set)** mode (T0.3) wraps whatever partial document the user types in `{ $set: <patch> } `and sends it here — only the fields present in the patch are touched, so concurrent edits to other fields on the document are never clobbered (unlike Replace, which rewrites the whole document).

Iteration 1 UI exposes **Insert**, **Replace** (via "Edit" → Replace mode), **Update fields ($set)** (via "Edit" → Update mode, T0.3), and **Delete**.

## 4. Delete safety

- `doc:deleteOne` is straightforward — confirmation modal for a single doc.
- `doc:deleteMany` is gated:
  1. UI calls `doc:confirmDeleteMany({ connectionId, dbName, collection, filterJson })` which runs `countDocuments(filter)` and returns `{ count, confirmToken }` if count > 0, or a refusal if unauthorized.
  2. UI shows a **two-step** confirm: user types the collection name to enable the final Delete button.
  3. UI calls `doc:deleteMany` with `{ ..., confirmToken }`. Main verifies token (JWT-less: just a short-lived nonce in memory), then deletes.
  4. If `count > 10_000`, the modal additionally shows a yellow warning and requires checking an "I understand this cannot be undone" box.

No "delete entire collection" in iteration 1 (that's `collection.drop`; out of scope).

## 5. UI flows

### Insert drawer
- Trigger: "Insert" button in the center header (`+` icon, primary).
- Opens a side drawer (400px, slides from right) with a full-height EJSON textarea preloaded with:
  ```
  {
    "_id": { "$oid": "<will be generated>" },
    "field": "value"
  }
  ```
  — actually, just `{ "" : "" }` with the cursor positioned. `_id` auto-omitted unless the user types one; Mongo assigns one.
- Buttons: `Insert` (primary), `Cancel`.
- On submit:
  - Parse EJSON locally; show inline error if fails.
  - **T2.7 — array routing**: if the parsed top-level value is a JSON array, the drawer classifies the payload (`classifyInsertPayload`) instead of always calling `doc:insert`:
    - a non-empty array of objects → `doc:insertMany` with `docsJson` set to the textarea's EJSON text; the Insert button reads "Insert N documents".
    - an empty array (`[]`), or an array containing any non-object item (string/number/`null`/nested array), is rejected client-side: Insert disabled, inline textarea error, no IPC call.
    - a single top-level object (including `{}`) is unaffected — still calls `doc:insert` exactly as before.
  - Call `doc:insert` (single doc); on success, close drawer, append-toast "Inserted {shortId}", and refresh result (re-run the current query).
  - On CONFLICT: show an inline banner inside the drawer.
  - **T2.7 — insertMany partial failure**: on an `insertMany` failure, read `details.insertedCount` from the thrown error. If it's a number `> 0` (some documents landed before an ordered-batch stop), show a banner stating how many of N documents were inserted, call `onPartialInsert` (refresh the grid so those rows are visible), and **do not** close the drawer or discard the user's text (re-submitting would only re-attempt the same already-inserted prefix, which the user must edit first — a known trade-off, not a bug). On a total failure (no `insertedCount`, e.g. the whole array is rejected up front), behavior is identical to the single-doc failure path: banner shown, no refresh, drawer stays open.

### Edit drawer
- Trigger: right-click row → `Edit`, or press `e` on selected row.
- Two modes, toggled by a pair of buttons at the top of the drawer, **Replace document** (default) and **Update fields ($set)** (T0.3):
  - **Replace document**: drawer shows the current EJSON of the document (pretty-printed, editable). `Save` calls `doc:replace` with `filter: { _id: <doc._id> }` and `docJson: <current text>`. If the user removes `_id` from the body, it is re-injected before submit (round-tripped via EJSON so BSON-typed `_id`s survive).
  - **Update fields ($set)**: drawer shows an *empty* EJSON textarea — deliberately not pre-filled with the document, so the affordance can't be used to "$set the whole doc" and reintroduce the clobber problem it exists to avoid. The user types only the field(s) to change. `Apply update` calls `doc:updateOne` with `filter: { _id: <doc._id> }` and `updateJson: { "$set": <parsed patch> }`. Client-side validation blocks (inline error, no IPC call) on: invalid EJSON, a non-object top level, an empty patch (`{}`), and a patch containing `_id`.
  - Both modes share the same "document has no `_id`" guard — the filter would otherwise collapse to `{}`, matching an arbitrary document.
- Success (either mode) → drawer closes, refresh (re-run the current query); errors surface in the drawer's inline `role="alert"` banner.

### Delete confirm
- Trigger: right-click → `Delete`, or `d` / `Backspace` on selected.
- Single-row: compact dialog "Delete document {shortId}? This cannot be undone."
- Multi-row (selection from W06): prompts the deleteMany flow (§4) with the collection name typed confirmation.

## 6. Result refresh

After any successful write:
- The current Run is re-executed automatically, preserving `page`, `builder`, `queryRaw`, etc.
- Re-run happens even if the user was on page 3; if the new result has fewer pages, pagination clamps.

## 7. Validation (client-side)

- Insert: body must parse as EJSON. A single top-level object is inserted via `doc:insert`. A top-level array routes to `doc:insertMany` and must be non-empty with every item a plain object; an empty array or an array containing a non-object item is refused client-side (Insert disabled, inline error, no IPC call). The server independently re-validates the same array rules — the client check is a UX convenience, not the source of truth.
- Edit — Replace mode: must parse; must not change `_id` (warn + refuse).
- Edit — Update fields ($set) mode (T0.3): patch must parse as EJSON; must be a JSON object at the top level; must be non-empty (refuse `{}`); must not contain `_id` (refuse — `_id` is immutable).
- Delete many: filter must be EJSON; non-empty object (refuse `{}` to avoid obvious mass-delete mistakes).

## 8. Acceptance criteria

- [ ] Insert adds a document and the refresh shows it if it matches the current filter.
- [ ] Pasting a top-level JSON array of objects into Insert calls `doc:insertMany` (not `doc:insert`) and inserts every document; a single top-level object still calls `doc:insert` unchanged.
- [ ] An empty array (`[]`) or an array containing a non-object item is rejected client-side: Insert disabled, inline error, no IPC call. The server (`DocumentService.insertMany`) independently rejects the same cases with `VALIDATION`.
- [ ] `insertMany` uses `ordered: true`; on a duplicate-key failure partway through the batch, exactly the documents before the failing one are persisted, and the service surfaces `CONFLICT` with `details.insertedCount` set to that count.
- [ ] On that partial failure, the Insert drawer stays open, shows a banner stating how many of N documents were inserted, and still triggers a grid refresh (`onPartialInsert`) so the partially-inserted rows are visible — it does not silently close or discard the user's text.
- [ ] Editing changes the document in place.
- [ ] Editing cannot remove the `_id`; the original is restored.
- [ ] The Edit drawer's Update fields ($set) mode sends only the patched fields via `doc:updateOne`, leaving unmentioned fields on the document untouched.
- [ ] Update fields ($set) mode is blocked for invalid EJSON, a non-object patch, an empty patch, a patch containing `_id`, or a document with no original `_id`.
- [ ] Deleting a single doc removes it from the result.
- [ ] deleteMany is gated: cannot run without typing the collection name; cannot run without `confirmToken`.
- [ ] Duplicate-key error surfaces as CONFLICT with a useful message.
- [ ] Schema-validation failure surfaces the server's validation errors.
- [ ] All write ops refresh the result automatically.

## 9. Test cases

### Integration (memory Mongo)
- **insert-happy.spec.ts**: insert a doc → `insertedId` present; `findOne` returns the doc.
- **insert-duplicate-key.spec.ts**: with a unique index → second insert returns CONFLICT.
- **insertMany (document-service.spec.ts, T2.7)**: happy path inserts every doc in the array; `docsJson: '[]'` rejects with `VALIDATION` and makes no driver call; an array containing a non-object item rejects with `VALIDATION`; an ordered batch with a duplicate key mid-array (`[{_id:2},{_id:1 (dup)},{_id:3}]`) rejects with `CONFLICT` and `details.insertedCount === 1`, and only the pre-existing doc plus the one before the duplicate are persisted — `_id:3` is never attempted, proving `ordered: true` stop-on-first-error semantics end-to-end.
- **replace.spec.ts**: replace keeps `_id`.
- **delete-one.spec.ts**: deletes one doc matching filter.
- **delete-many-gate.spec.ts**: call without confirmToken → VALIDATION; call with invalid token → VALIDATION; happy path works.
- **delete-many-count-cap.spec.ts**: with 10 000 docs, UI would require extra confirm; server honors it once token is valid.
- **authorization.spec.ts**: unprivileged user → UNAUTHORIZED.

### Component
- **insert-drawer.spec.tsx**: invalid EJSON → inline error, no IPC call; valid → IPC called with EJSON string; (T2.7) an array payload calls `doc.insertMany` (not `doc.insert`) and closes on success; a single-object payload still calls only `doc.insert` (regression guard); `[]` and an array with a non-object item disable Insert and make no IPC call; a partial-failure rejection (`CONFLICT` with `details.insertedCount`) keeps the drawer open, shows a "N of M inserted" banner, and calls `onPartialInsert` instead of `onClose`/`onInserted`; a total failure (no `insertedCount`) preserves the existing single-doc banner/no-refresh behavior.
- **edit-drawer-id-reinjection.spec.tsx**: edit with `_id` removed → warning; Save still sends original `_id` (Replace mode).
- **edit-drawer-update-set.spec.tsx** (T0.3): Update fields ($set) mode sends a partial patch via `doc.updateOne` touching only the edited field (never `doc.replace`); defaults to Replace mode when untouched; blocks (no IPC call) on invalid EJSON, non-object top level, empty patch, a patch containing `_id`, and a document with no original `_id`; exactly one textarea renders in the DOM regardless of mode.
- **delete-single.spec.tsx**: single-row dialog → confirm → `doc:deleteOne`.
- **delete-many.spec.tsx**: type mismatched name → confirm disabled; typing correct name → confirm enabled.
- **refresh-after-insert.spec.tsx**: successful insert → `api.query.find` re-called with same args.

### E2E
- **crud.e2e.ts** (`w09-doc-edit-delete.e2e.ts`): Insert → row appears → Edit (Replace mode) → change a field → row updates → Delete → row gone.
- **w09-doc-edit-delete.e2e.ts** (T0.3): Edit → Update fields ($set) mode → patch one field of a multi-field document → row shows the patched field changed **and** the untouched fields still present, proving `$set` semantics end-to-end.
- **w09c-insert-many.e2e.ts** (T2.7): paste a 2-document JSON array into Insert → button reads "Insert 2 documents" → both new rows appear and the drawer closes.
